# MS6050 DMP Design

Date: 2026-04-25
Status: approved in chat, pending user review of this written spec

## Goal

Adapt the existing `ATK_MS6050 + eMPL` package to the current `STM32F103C8 + StdPeriph + FreeRTOS + USART1` project, then output `pitch / roll / yaw` continuously over the existing serial port.

Target behavior:

- `pitch` and `roll` should be stable and accurate for normal use.
- `yaw` should be usable as a relative heading and may drift slowly over time.
- The output path must not disturb DMP sampling timing.
- `uvprojx` must not be modified automatically.

## Hardware Mapping

Use only GPIOs that do not conflict with the current project:

- `PB10`: software-I2C `SCL`
- `PB11`: software-I2C `SDA`
- `PB12`: `INT` input from MS6050
- `PC0`: `AD0`, driven low to force I2C address `0x68`
- `PA9/PA10`: keep existing `USART1`
- `PC13`: keep existing board LED

Rationale:

- `PA9/PA10` are already used by `USART1`.
- `PC13` is already used by LED.
- `PB10/PB11/PB12/PC0` are available in the current template and keep the sensor path isolated from the debug serial path.

## Driver Architecture

Keep the `HARDWARE/ATK_MS6050` directory, but rewrite the board-adaptation layer for this project.

Layers:

1. `atk_ms6050_iic.*`
   Bit-banged I2C using StdPeriph-style GPIO access on `PB10/PB11`.

2. `atk_ms6050.*`
   Base sensor driver:
   - register read/write
   - reset
   - scale/rate configuration
   - raw gyro / accel / temperature access
   - AD0 control and INT pin setup

3. `eMPL/*`
   Keep the DMP / motion-processing logic intact as much as possible.
   Only adapt its platform hooks:
   - GPIO / I2C access hooks
   - millisecond timestamp provider
   - delay provider

4. Project-facing wrapper
   Add a small wrapper API that the application tasks use instead of calling deep `eMPL` entry points directly.

## Porting Strategy

The current `ATK_MS6050` code is copied from an `F407 + HAL` project, so the adaptation work is not just path cleanup. The following must be rewritten:

- HAL GPIO clock macros -> StdPeriph clock enable calls
- HAL GPIO init structs -> StdPeriph `GPIO_InitTypeDef`
- HAL pin write/read -> StdPeriph or direct register access
- `HAL_GetTick()` -> FreeRTOS / project time source wrapper
- include paths such as `./BSP/...` -> local project paths
- unnecessary includes such as `usart.h` in the low-level sensor driver

The DMP algorithm files themselves should be changed as little as possible to reduce regression risk.

## FreeRTOS Design

Create two application tasks:

1. `ms6050_task`
   Responsibility:
   - initialize the sensor
   - initialize DMP
   - wait for data-ready events
   - read FIFO / DMP output
   - update the latest shared attitude result

2. `ms6050_uart_task`
   Responsibility:
   - periodically read the latest attitude result
   - print formatted `pitch / roll / yaw` over `USART1`

Timing:

- sensor/DMP side should run near the configured DMP output rate
- UART printing should be intentionally slower, around `10Hz`, to reduce serial blocking impact

Synchronization:

- use a simple shared structure protected by a FreeRTOS critical section or a mutex
- keep the protected region short

## Accuracy Strategy

This project can provide useful DMP-based attitude output, but accuracy has an upper bound set by the sensor hardware:

- `pitch / roll`: expected to be stable and accurate for normal balancing / pose / tilt applications
- `yaw`: expected to be a relative heading that may drift because no magnetometer is present

Measures to improve practical accuracy:

- require the board to remain stationary during startup calibration
- keep DMP timing stable
- separate sampling from UART printing
- use the INT pin instead of pure blind polling
- avoid modifying core eMPL fusion logic unless a concrete bug is proven

Non-goal:

- absolute north-referenced heading

## Error Handling

Initialization failures should be detectable and easy to diagnose:

- sensor ID read failure
- I2C ACK failure
- DMP init failure
- FIFO overflow / repeated data acquisition failure

Planned handling:

- return explicit error codes from the low-level driver
- convert task init failures into visible UART messages
- keep the output task from printing invalid attitude data before initialization succeeds

## Validation Plan

Validation should focus on both function and timing:

1. Build validation
   - all adapted source files compile under current Keil ARMCC5 configuration

2. Bring-up validation
   - sensor init succeeds
   - device ID is read correctly
   - DMP init succeeds

3. Functional validation
   - serial port prints continuous `pitch / roll / yaw`
   - manually tilt forward/backward and verify `pitch` changes as expected
   - manually tilt left/right and verify `roll` changes as expected
   - rotate in plane and verify `yaw` changes continuously

4. Stability validation
   - keep the board still and observe that `pitch / roll` remain near zero with small noise
   - observe `yaw` relative drift over time and confirm it remains acceptable for the stated goal

## Constraints And Assumptions

- The project remains on `STM32F103C8`.
- The project uses StdPeriph, not HAL.
- FreeRTOS remains enabled and available.
- Existing `USART1` is used for output.
- No automatic modification of `uvprojx`.
- The sensor module is wired according to the mapping in this document.
